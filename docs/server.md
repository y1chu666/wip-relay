# 服务端说明

中继服务端只做两件事：接收并保存各设备的状态记录，供其他设备读取。它不接触文件内容，也不持有内容密钥。

## 职责

- 校验请求签名与时间窗口，拒绝重放。
- 保存状态记录与吊销记录，按序号取新。
- 维护频道与设备列表，处理注册、吊销与退役。
- 记录必要的日志，供运维排查。
- 对请求头、整条请求、回应与空闲连接都设有时限：慢速连接不会长期占住资源（正文收完之前不会验签，因此只限读头不够）。

不负责：内容同步、冲突解决、跨中继复制、账号体系。

## 存储

使用嵌入式键值存储（bbolt），单文件，随服务端启动挂载。

- 数据目录与配置文件分离。
- 记录按频道与设备组织，序号单调。
- 删除即删除，不保留墓碑；吊销名单单独存放并长期保留。
- 吊销名单的条数由配置约束（默认一千零二十四条），达到上限之后不再接受新的吊销与退役。吊销只增不减，反复注册再退役就能把它堆到任意长，而每次上报都要整份回送，因此这里必须有个上限；需要更多时由运维调高该值。
- 备份即复制数据文件，恢复即替换数据文件。

## 子命令

- `serve`：启动服务，直到收到中断或终止信号。
- `init`：生成配置样例，并写下一枚注册凭证；凭证只显示一次，服务端只保存它的摘要。
- `list`：列出频道、设备、状态记录与吊销名单，用于确认状态。
- `reload`：请正在运行的服务重新读取配置。重载靠数据目录中的请求文件完成，不依赖信号，各平台行为一致；配置写错时服务沿用原配置并留下日志。
- `recover`：清除吊销名单中的指定条目，用于设备全部失联的极端情形。
- `version`：输出版本信息。

`list` 与 `recover` 直接打开存储文件，因此两者都需要先停止服务。存储同一时间只允许一个进程打开，这既是限制，也避免了在服务运行中改动数据。

## 密钥

服务端密钥是自行生成的 Ed25519 密钥对，存放于数据目录，权限只放开给属主。密钥一经生成不再更换：客户端在首次配对时钉住这把公钥，换了等于换了服务端，全部设备都要重新配对。启动时日志会打印服务端指纹，便于在设备上核对。

## 配置

配置为带版本号的 TOML 文件，与客户端侧同构，可手工编辑。主要内容包括：

- 监听地址与端口
- 数据目录
- 传输要求：最低级别、证书与私钥路径
- 限流与各项上限
- 日志级别

配置中的相对路径按配置文件所在目录解析，使服务端行为不随启动目录变化。配置是运行参数的唯一事实来源：设备注册完毕后把注册开关关掉，再用 `reload` 让它立即生效，不必重启。

配置中不得出现真实域名、设备名等信息，示例文件只写占位值。

## 跨平台

发布目标为 Linux 与 Windows。单一静态二进制，不依赖外部运行库；配置文件与数据目录使用各平台惯用位置。

## 部署建议

- 置于反向代理之后，或直接启用 HTTPS。
- 只暴露必要端口。
- 数据目录设最小权限，并定期备份。
- 以非特权用户运行。
- 置于反向代理之后时，来源地址维度会看到代理的地址，限流因此退化成全局计数；按真实来源限流应在代理侧完成（例如按真实客户端地址限流）。服务端不解析转发头，也不信任它们，以免仅凭一个可伪造的头就绕过限流。

## 已知限制

- 每台设备在中继上只保留一条记录，新记录覆盖旧的。`limits.records_per_device` 目前只参与配置校验，不决定保留几条。
- 被吊销与被退役的设备仍占着 `limits.devices_per_channel` 的名额，名额不会回收：吊销只记名单、不移除设备，免得「谁被吊销过」这件事被抹掉。持有注册凭证的人若把名额占满，后来的设备就注册不进来，此时调高上限，或用 `recover` 子命令。
- 判重表与限流桶的清理是遍历式的，且在全锁内进行：设备与来源地址很多时，这部分开销会随时间放大（前提是凭证在手、并发出大量请求）。
- 存储文件损坏时，受影响频道的记录、设备与吊销列表会整体读不出来，请求以 5xx 结束。这不是经由接口能造出的输入，但本地文件一出问题，影响面会从一条放大到整个频道。

## 运维

- 日志按级别输出到标准错误，交由系统日志设施收集。
- 限流触发与签名失败必须留痕。
- 版本升级只替换二进制；数据结构有变更时提供迁移步骤。
